# 已發布知識再結晶 (Published Knowledge Re-crystallization)

本工作流用於吸收既有貼文，而不是維護既有貼文。它把已發布文章視為「已經過貼文管道術語化的知識產物」，透過重新閱讀正文、反推問題域與因果鏈，產出新的結晶報告。

本流程的輸出是**報告**，不是貼文。若使用者決定發布再結晶結果，應在人工審查後另行交給 `init-handoff` 與 `publish-article`。

> [!IMPORTANT]
> 本流程是 `crystallize-report.schema.yaml` 中 `recrystal_only` 區塊的**唯一**套用者：其 `principles`（密度下限、條件性結構化、擴張上限）、`quality_gate` 與 `target_path` 覆寫只在本工作流生效。一般 `/crystallize-report` 只跑 shared 的 `principles`／`quality_gate`，不讀 `recrystal_only`——shared 清單中已無任何再結晶條目，故兩邊互不污染。
> 輸出佈局見 `recrystal_only.target_path`，覆寫 schema `CRITICAL_INSTRUCTION` 的 `TARGET_PATH`（詳見 §7）。

---

## 0. 邊界聲明 (Boundary Contract)

本工作流必須保持自洽且無耦合：

1. **不修改 `content/`**：嚴禁直接覆寫、刪除或重命名既有貼文。
2. **不執行 `reanchor-posts`**：術語錨點維護屬已發布內容維護層，不屬本流程。
3. **不產生 handoff JSON**：`handoff.posts.json` 與 `handoff.terms.json` 由 `init-handoff` 負責。
4. **不發布文章**：發佈管線由 `publish-article` 負責。
5. **不以既有 front matter 為權威**：既有 `title`、`tags`、`series` 僅作觀察資料，不得直接視為主題真相。

## 1. 輸入解析 (Input Resolution)

| 輸入 | 處理方式 |
| :--- | :--- |
| 指定母系列主題 | 僅處理該系列候選貼文 |
| 指定貼文路徑清單 | 讀取清單中所有貼文全文 |
| 指定 backlog 項目 | 依據 backlog 中的候選清單處理 |
| 未指定貼文 | 先產出候選清單與疑似邊界文章，不進入重寫 |

### 1a. 單系列 Session 原則

每次 session 只能處理一個母系列。若候選文章跨越多個母系列，必須先拆成多次 session。

允許讀取：
- 該母系列候選文章全文。
- 全站 taxonomy 或 backlog 規則。
- 最多 3-5 篇邊界文章的摘要。

禁止讀取：
- 所有貼文全文。
- 前一個系列 session 的詳細推理紀錄。
- 與本系列無關的既有分類結論。

被多個系列共用的前提（見 backlog「共用前提一致性參考」）不抽成跨系列報告，也不跨 session 引用；用到它的系列必須**就地自含重述**，措辭與該參考一致。跨系列重複這些前提是自包含的必要條件，不是污染。

### 1b. 模式旗標 (Mode Flags)

| 旗標 | 行為 |
| :--- | :--- |
| `--scan-only` | 只執行到候選清單與疑似邊界文章盤點（等同上表「未指定貼文」列的行為），**不進入 §2 正文反推與後續重寫**。用於先確認系列邊界與候選範圍，再決定是否啟動完整重寫 session。 |
| `--force-write` | 允許將**可交付產物**寫入磁碟，路徑與限制見 §7；未提供時預設只在對話輸出草稿。 |

兩旗標皆未提供時，預設行為為「完整重寫 + 僅對話輸出」。

## 2. 正文反推 (Text-first Reconstruction)

每篇候選貼文必須先忽略既有 `tags` 與 `series`，從正文重建以下資訊：

```markdown
文章：
核心問題：
實際處理的對象：
不是在處理什麼：
緣起因果（觸發事故／症狀／這個問題當初怎麼發生）：
主要因果鏈：
具體案例（支撐主張的真實事件與細節）：
主要概念：
與同系列文章的差異：
與同系列文章的重疊：
可能污染詞：
不可替代角色：
未展開的潛在子問題（正文開啟但未回答／一筆帶過的問題）：
正文假設但未證成的前提（被當成已知、實則需要就地建立的東西）：
是否暗藏多個核心問題（若是，列出可拆分的子問題）：
```

`緣起因果` 與 `具體案例` 是後續壓縮下限（§4b）與因果覆蓋閘門（閘門 18、19）的比對來源，必須據實逐篇記錄；漏記等於默許後續被靜默吞掉。

最後三欄是**生成式展開**的來源（§3.6 展開機會盤點、§4b 展開下限的輸入）：原貼文常因篇幅或當時脈絡而把潛在深度壓在一句話裡，這三欄逼出那些被原文描述蓋住、值得展開成段落、附錄或另一 slot 的材料。漏抽＝默許「被既有描述限制」。

若正文不足以支撐明確核心問題，該文不得被重寫為獨立報告；應標記為「併入」「降級為段落」或「移出本系列」。

## 3. 系列級重整 (Series-level Recomposition)

在處理單篇之前，必須先建立系列地圖：

1. **問題域界定**：此系列真正處理哪一類治理、架構、認知或協作問題。
2. **文章角色分配**：每篇文章在系列中承擔的不可替代功能。
3. **因果順序**：系列內文章的閱讀順序應由因果或依賴關係決定，不由發布日期決定。
4. **重疊處理**：預設保留分篇，先分工、再去重，最後才考慮合併。
   - **去重的對象只有「逐字重複的前提陳述與結論陳述」**；各篇的緣起因果、觸發事故與具體案例是分篇的**證據多樣性**，禁止以「重複」為由去重或抽象掉。兩篇殊途同歸時，兩個事故都留——它們證明同一結論在不同情境皆成立。
   - 問題相近但角度不同：保留分篇，明確各自角色。
   - 前提重複但結論不同：抽出共享前提，其他文章短引。
   - 術語重複但用途不同：統一定義，各篇保留用途。
   - 核心問題相同但案例不同：優先改為主文加案例段，或一篇主文、一篇附錄型報告。案例段必須保留各案例的緣起因果與細節，不得壓縮成一句帶過。
   - 核心問題、因果鏈、結論角色皆相同：才允許合併。合併時仍須把各來源的緣起因果與案例**全部吸收進保留篇**，不得隨被合併篇一起丟棄（漏掉者進損失帳本，見 §4b）。
   - 合併會使單篇承載超過一個核心問題：禁止合併，必須保留分篇或重新分工。
   - **一篇來源貼文暗藏多個核心問題（§2 反推卡末欄為真）：應拆分成多個 slot，而非預設一篇對一報告。** 這是合併的對稱動作——偵測「來源超載」並拆深，是被鼓勵的展開，不是過度切分；拆出的每個 slot 仍須各自有不可替代角色與明確邊界。
5. **邊界文章判定**：不屬於本系列的文章應移出 backlog，不在本 session 中重寫。
6. **展開方向盤點（必填）**：在重寫單篇之前，必須完成 backlog「展開方向盤點表」。四個展開類型（共用前提就地自含、概念地圖／詞彙表、反例與不適用邊界、結構化資產）逐格給定固定狀態值，不允許留空；既有「可順勢補齊的基礎方向」必須逐項落入某格。此表是**防守式的基礎補齊**（補足前提、定義、反例、結構）。
   - **展開機會盤點（生成式，必填）**：除上述防守式補齊外，必須另就 §2 反推卡末三欄（潛在子問題、未證成前提、暗藏多核心）逐篇盤點，列出三類生成式展開機會並各自給去向（`本次展開` / `本次不展開＋理由` / `移入後續 backlog`）：
     1. **拆分**：來源超載 → 拆成多 slot（見步驟 4）。
     2. **潛在深化**：原文一句帶過、實則值得發展成段落／附錄／另一 slot 的深度。
     3. **跨篇湧現主題**：多篇合讀才浮現、單篇都沒明說的問題或連結。
   - 此盤點防的是「因原貼文 terse 而少寫」；它與 §4b 擴張上限不衝突——上限守「可回溯到問題域」，本盤點守「不被既有描述當成深度天花板」。
7. **報告清單鎖定（必填）**：在進入 §4 之前，必須凍結一份**報告清單**，每個 slot 明列固定四欄：`核心問題 / 不可替代角色 / 緣起來源 / 邊界`。可給臨時代號或工作標題作標籤（僅為內部辨識，不是 §6 的最終 metadata，不得倒推正文）。
   - **兩層分置**：`緣起來源` 指向候選貼文，屬 provenance，整份鎖是**內部檢核產物**——依 §5、§7 只留 session 內、禁落盤。series-map 只呈現**去痕跡後的 slot**（`核心問題 / 不可替代角色 / 邊界` 與閱讀順序），不含來源 slug 或篇名。
   - 此清單對 §4 是**鎖**：§4 重寫**不得減少 slot 數，也不得把兩 slot 寫成一篇**。
   - 要合併或砍掉任一 slot，必須同時 (a) 進損失帳本附理由（見 §4b）、(b) 重新通過步驟 4 的合併條件（核心問題、因果鏈、結論角色皆同構才准）。**靜默併篇或漏寫一篇視為未完成。**
   - **slot 數可高於候選貼文數**：當步驟 4 拆分或步驟 6 展開機會盤點判定該拆深時，鎖定一個比候選數更多的 slot 數是**被鼓勵的**，不算過度切分（過度切分由閘門 8「單篇不超過一個核心問題」與「每 slot 須有不可替代角色」把關）。
   - 鎖只防「篇數塌縮」；步驟 4 與閘門 8 仍防「過度切分」。兩端都不准靜默處理。

步驟 6、7 任一未完成，不得進入 §4 重寫。

## 4. 文體合約 (Style Contract)

文體採**嚴格期刊論文層級的論證嚴謹度**：每個通用化結論都必須由回推因果與具體個案**賺得**，主張、邊界、反例齊備，不留未證成的跳躍。

> [!IMPORTANT]
> 「嚴格」指**論證嚴謹，不是學術腔或形式堆疊**。期刊級嚴謹（通用化由因果與證據支撐）與形式主義（空泛學術腔、為像論文而疊章節）是兩回事——好期刊文章嚴謹但不浮誇。因此本節仍**保留工程技術文章的可讀性**：shared 原則的句子概念上限、抗摘要化連結組織照常生效，下方「避免」清單與本嚴謹度標準並行不悖。

每篇重寫報告必須包含：

1. **問題定義**：本文要解決的誤判、風險或治理問題。
2. **背景脈絡**：問題在什麼實務情境中出現。
3. **核心主張**：本文提出的判斷、模型或取捨。
4. **因果鏈**：問題如何形成、擴散，並造成後果。
5. **邊界條件**：本文主張不適用或容易被誤用之處。
6. **實務含義**：讀者應如何改變判斷、設計或流程。
7. **收束結論**：將全文壓縮成一個可記憶的概念。

避免：

- 空泛學術腔。
- 為了像論文而堆疊形式章節。
- 沿用未經正文支持的原貼文術語。
- 未證成的宏大結論。
- 只把原文改寫得更順，卻沒有補足因果。
- **主張先行、再貼裝飾性例子**：個案應是論證的起點與骨幹，不是事後插圖（見 §4c）。
- **把個案抽象成「某次經驗顯示」而抹掉其具體因果路徑**：回推因果要寫成可檢查的鏈，不是概括。

### 4a. 結構化表達優先 (Structured Expression)

當概念能以可檢查結構表達時，應優先使用 Mermaid 圖或 example code，而不是只用抽象散文描述。

優先使用 Mermaid 的情境：

- 因果鏈、決策流程、治理管線、狀態遷移、權責邊界。
- 多文章之間的依賴、分工與閱讀順序。
- 污染源、信任邊界或資料流的傳播路徑。

優先使用 example code 的情境：

- 契約、schema、設定、目錄結構、權限模型、API 邊界。
- 可用短程式碼展示的正反例。
- 需要把抽象規則落成可執行或可檢查形狀的段落。

使用限制：

- Mermaid 與 example code 必須承載論證，不得作為裝飾。
- 每個圖或 code block 前後都要有 prose 說明：先說它解決什麼問題，再解釋讀者該看什麼。
- 若圖或程式碼會迫使單篇過厚，應拆成系列內另一篇或附錄型報告，而不是塞回主文。

### 4b. 密度下限、壓縮下限、展開下限與擴張上限 (Density / Compression / Expansion Floor & Expansion Ceiling)

當貼文降為「引子」、報告以重鑄為目標時，需同時鎖住四端，否則「更完美」不可驗收。**只鎖密度與擴張、不鎖壓縮，會讓重寫收斂到「精煉合併」——緣起的因果與細節被靜默吞掉；不設展開下限，則報告會停在原貼文的描述深度，潛在材料被既有描述封頂。**

先區分兩種因果，兩者都要保，但保護機制不同：

- **證成因果（justificatory）**：這個抽象主張*為何成立*。由下方**密度下限**保護。
- **緣起因果（genetic）**：這個問題*當初怎麼發生*——觸發事故、症狀、那條凌亂的真實路徑。由**壓縮下限**保護。這正是最容易被「抽象成乾淨原理」而吞掉的部分。

**密度下限**：每個核心主張至少具備以下三項，缺一者視為密度不足：

1. 因果機制：主張為何成立，而不只是斷言成立。
2. 邊界條件：主張不適用或容易被誤用之處。
3. 一個反例或失敗案例：展示主張被違反時會發生什麼。

此外，**當主張涉及流程、契約、邊界、狀態或因果傳播時**，必須附一個結構化表達（Mermaid 或 example code，見 §4a）；純概念或定性主張不得為形式而硬塞圖表。

**壓縮下限（緣起保全）**：重寫後報告的因果鏈必須**覆蓋** §2 反推卡裡每一篇候選貼文記下的「緣起因果」與「具體案例」。

- **因果覆蓋**：反推卡的每一條緣起因果步驟，必須在某篇報告中以具體形式存活；不得抽象成「因故」「基於某些原因」這類吞掉細節的概括。
- **損失帳本（內部產物）**：任何被刪、被併、被抽象掉的緣起因果步驟或具體案例，必須逐筆記入「損失帳本」並寫明理由（如真屬重複陳述、或已被另一案例完整涵蓋）。**靜默丟棄視為未完成**，比照 §9 紀律。
- 損失帳本含原貼文片段，依 §5、§7 **只能留在 session 內部脈絡，即使 `--force-write` 也嚴禁落盤**，亦不得進入任何可交付產物。
- 去重與合併只能消除*重複的陳述*，不能成為丟棄*緣起因果與案例*的藉口（見 §3 步驟 4）。

**展開下限（主動增益）**：原貼文的描述是**種子與下限，不是天花板**。因篇幅或當時脈絡被壓成一句的潛在深度、未證成的前提、暗藏的多核心問題（§2 反推卡末三欄、§3.6 展開機會盤點），凡判定為 `本次展開` 者，必須被實際發展成段落、附錄或另一 slot；**因 terse 而少寫、讓報告停在原文涵蓋範圍，與因膨脹而失焦同屬缺陷**。此處沿用 shared 原則的「主動增益」（以技術外推、重建辯證路徑提供解析度，嚴禁空洞填充）。

**擴張上限**：報告可超出原候選貼文的範圍以補足因果與展開潛在深度，但每一段新增論證必須能回溯到**本系列的問題域**（不是回溯到「原文寫過的範圍」），或為使報告自包含所需的就地前提重述。無法回溯者，移入展開盤點表的「移入後續 backlog」，不得直接膨脹主文——這條防止「引子」被無限擴寫成另一篇失焦綜述。

三者各守一端：**密度下限**守證成因果、**壓縮下限**守既有緣起不被吞、**展開下限**守潛在深度不被既有描述封頂；**擴張上限**則是唯一的反向守門，防膨脹無關新論。展開下限與擴張上限的分界線是「可否回溯到系列問題域」：可回溯且原文未充分發展 → 展開；不可回溯 → 進 backlog。四者都以「進帳本／進盤點／進 backlog 並附理由」取代「靜默處理」。

### 4c. 個案主軸與回推因果 (Case-spine & Causal Back-inference)

本模式的預設 Structure 為 **Analytical Essay（個案驅動）**：從具體個案推導分析、最後昇華為通用原理，而非先宣告原理再找例子。這是 §4b 壓縮下限在結構層的體現——把「緣起因果」寫成可檢查的回推鏈，而不是概括掉。

- **個案為主軸**：每個核心主張**盡可能**以 §2 反推卡的「具體案例」為起點與骨幹——先擺出真實發生的事件／症狀／失敗，再從中長出主張。個案是論證的證據骨架，不是事後插圖。確屬純概念的主張仍須附 §4b 密度下限要求的反例。
- **回推因果（causal back-inference）**：論證方向是從個案的**結果／症狀回推到成因**——重建「這件事當初為何、如何發生」的因果鏈，而非從抽象機制正向演繹。緣起因果因此被寫成可檢查的回推鏈，而非「某次經驗顯示」式的概括。
- **論證骨架順序**（每個核心主張）：

  ```text
  具體個案 → 回推因果鏈（為何發生） → 核心主張（可遷移判斷） → 邊界條件 → 通用化
  ```

- **與 §4 七章節相容**：個案與回推填充「背景脈絡」「因果鏈」「核心主張」，通用化收於「收束結論」。回推出的因果鏈與結構邊界，依 §4a 優先以 Mermaid／example code 承載。

## 5. 輸出去痕跡化 (Output De-tracing)

再結晶報告必須把原貼文視為輸入材料，而不是輸出依賴。所有可交付產物都應呈現為因果完備、語義自洽、沒有再生成痕跡的完整內容。

### 5a. 去痕跡原則

1. **不引用原貼文**：可交付產物的正文、metadata、附錄不得指向原貼文 slug、路徑或檔名。
2. **不保留加工痕跡**：不得出現「本文重寫自」「來源貼文」「原文」「候選文章」「再結晶」等暴露生成管道的表述。
3. **不要求外部閱讀**：讀者不需要知道原貼文存在，也能理解報告的問題、前提、因果、結論與邊界。
4. **吸收後重述**：原貼文中的有效洞察必須被吸收、重組與重新證成，而不是以引用或摘要形式拼接。
5. **系列關係自然化**：若報告屬於系列，僅呈現自然的概念分工與閱讀順序，不揭露其由哪些舊貼文重組而成。

> [!IMPORTANT]
> **去的是管道痕跡，不是緣起因果。** 去痕跡化要抹除的是**來源/管道識別痕跡**——slug、路徑、檔名、「本文重寫自」「原文」「再結晶」這類暴露生成管道的措辭。它**不**包含**實質的緣起因果**：觸發問題的具體事故、症狀、那條真實發生過的因果路徑。後者必須被吸收後**以具體形式重述**（§4b 壓縮下限），不得連同管道痕跡一起抽象掉。
> 判準：抹除後讀者仍**不知道**這是從舊貼文重組的（管道隱形），但**完全知道**這個問題當初如何發生、如何擴散（緣起可見）。兩者同時成立才合格。

**適用範圍**：本節（含 §5a.2 對「再結晶／重寫自」等措辭的禁制）治理的是**報告正文、導讀與系列地圖的敘事內容**。§6c 的稽核表頭（`Model`／`Agent`／`Source: reconstruction`）是 schema 規定的送審稽核 metadata，**不在本節約束範圍內**——但該表頭仍須遵守本節對「來源貼文 provenance」的禁制：不得含原貼文 slug、路徑、檔名或指向特定來源篇。

工作過程中可以使用候選清單與原貼文路徑作為內部輸入，但這些痕跡不得進入可交付產物。若執行者需要保留操作紀錄（含損失帳本），只能保留在 session 內部脈絡，不輸出為報告、導讀或系列地圖。

## 6. Metadata 再結晶 (Metadata Re-crystallization)

重寫完成後，才重新產生 metadata。不得先整理 metadata 再倒推正文。

**落點先講清楚**：再結晶後的 `series` 與 `tags` 一律記入 **series-map.md**（`series` 為系列級、`tags` 逐報告列），**不附加於 `report.zh-TW.md`**。`report.zh-TW.md` 正文以結論收束，**結尾嚴禁出現 `series`／`tags`／「建議 metadata」這類區塊**——它不是報告敘事，是生成管道痕跡，違反 §5；且 metadata 的最終定稿屬 `publish-article`，此處只是送審用的問題域描述。

### 6a. Series

`series` 必須描述問題域，而不是描述批次、日期或生成來源。

良好格式：

```toml
series = ["信任邊界與驗證瓶頸：AI 協作中的漂移、幻覺與外部裁決"]
```

### 6b. Tags

每篇最多 3-5 個主題 tags。tags 必須具備檢索價值，且由正文支持。

禁止把以下項目當作主題 tags（**本清單為禁用 tag 的唯一權威**，backlog「Taxonomy 去污染規則」引用此處，不另複述）：

- 文體：`分析論述`、`分析論文`、`技術筆記`、`經驗報告`
- 全域背景：`AI 代理人`
- 生成或段落痕跡：`導言`、`反思`、`實務對比`
- 模糊形容：`形狀`、`差異`

文體應改由 `article_type` 或報告 schema 的結構選擇承載。

### 6c. Front Matter（稽核表頭）

可交付報告的 HTML front matter 區塊依 `crystallize-report.schema.yaml` 的 `front_matter.template` 填寫（`Structure`／`Date`／`Model`／`Agent`／`Source`），本模式 `Source` 取 `reconstruction`。

此區塊是**送審階段的稽核 metadata，不是報告正文**，須與 §5 分流看待：

- **§5「無再生成痕跡」治理的是正文敘事，不及於本稽核表頭。** 因此 `Model`／`Agent`／`Source: reconstruction` 在此是「誠實宣告由誰、以何方法產出」的稽核值，是審查所需，不視為偷渡的痕跡。
- 釐清兩種痕跡的分軸：§5 真正要抹除的是**來源貼文 provenance**（從哪些舊貼文重組）。`Model`／`Date`／`Agent` 不洩漏這個；本表頭**仍嚴禁**寫入原貼文 slug、路徑、檔名或「重寫自某篇」這類來源指向。
- 本報告非貼文。當它經人工審查後進入 `publish-article`，此稽核表頭由發布管線**剝除或重做**為貼文 front matter（title／tags／series／date），不隨報告發布。

## 7. 輸出格式 (Outputs)

預設只在對話中輸出 Markdown 草稿，不寫入磁碟。

若使用者明確提供 `--force-write`，**只有可交付產物**可寫入磁碟，且僅限以下三類路徑：

```text
.agent-scratch/recrystal-<YYYY-MM-DD>-<suffix>/series-map.md
.agent-scratch/recrystal-<YYYY-MM-DD>-<suffix>/<report-slug>/report.zh-TW.md
.agent-scratch/recrystal-<YYYY-MM-DD>-<suffix>/guide.zh-TW.md
```

內部檢核產物（反推卡、候選清單、擴張去向標記等，見 §9）**即使在 `--force-write` 下也嚴禁寫入磁碟**——它們含原貼文 slug、路徑與原文片段，落盤即等於把可交付產物正要抹除的來源痕跡保存下來。內部檢核產物只能留在對話／session 脈絡。

`series-map.md` 必須位於 session 根目錄；每份報告必須放入自己的 `<report-slug>/` 子目錄。若本次只產出一篇主報告，省略 `guide.zh-TW.md`。

此佈局**覆寫** `crystallize-report.schema.yaml` 之 `CRITICAL_INSTRUCTION` 的 `TARGET_PATH`：`recrystal-` 前綴目錄是辨識「重新結晶」的必要區隔，`series-map.md` 與 `guide.zh-TW.md` 皆為本流程正常產物，均不觸發該規則的 abort。

輸出物：

1. **series-map.md**：抽象後的系列邊界、文章角色與閱讀順序，**內含已填妥的展開方向盤點表**（四類展開狀態無留空），**並承載再結晶後的 metadata——系列級 `series` 與逐報告 `tags`**（§6）；不得包含原貼文 slug、路徑或檔名。
2. **report.zh-TW.md**：再結晶後的主報告或文章草稿，不得包含原貼文引用、路徑或再生成痕跡。**正文以結論收束，結尾不得附加 `series`／`tags`／「建議 metadata」等任何 metadata 區塊**（metadata 落於 series-map.md，見 §6）。
3. **guide.zh-TW.md**：若單次產出兩篇以上報告，提供自然化閱讀順序與關係拓撲；不得揭露舊貼文重組來源。

## 8. 品質閘門 (Quality Gate)

產出前必須確認：

1. 每篇文章有明確核心問題。
2. 每篇文章在系列中有不可替代角色。
3. 重寫後因果鏈比原文更完整。
4. 重寫後可讀性比原文更高。
5. 未沿用正文無法支持的既有 tags。
6. 文體型 tags 已移出 tags。
7. 若兩篇文章核心問題相近，已優先重新分工；只有在核心問題、因果鏈、結論角色皆相同時才合併。
8. 合併後的單篇未承載超過一個核心問題。
9. 能用 Mermaid 或 example code 清楚表達的流程、契約或邊界，已適度結構化。
10. 新系列名稱描述問題域，而非描述寫作批次。
11. 報告正文自包含，不依賴讀者讀過原貼文。
12. 可交付產物的正文、導讀與系列地圖沒有原貼文引用、檔案路徑、候選清單或再生成痕跡（§6c 稽核表頭依 §5「適用範圍」除外，但其本身亦不得含原貼文 slug／路徑／來源指向）。
13. 未修改 `content/`，未產生 handoff JSON，未執行發布。
14. 展開方向盤點表四類已全部給定固定狀態值，無留空；選 `不需要`／`移入後續 backlog` 者皆附理由。
15. 每篇報告的核心主張皆達密度下限（因果機制＋邊界條件＋反例；涉及流程／契約／邊界／狀態／因果傳播者另附結構化表達）。
16. 新增論證皆可回溯至本系列候選貼文問題域，或為自包含所需的就地前提重述；不可回溯者已移入 backlog 而非膨脹主文。
17. 共用前提採系列內就地自含重述，措辭與「共用前提一致性參考」一致；未抽成跨系列報告，未跨 session 引用。
18. **因果覆蓋**：§2 反推卡記下的每一條緣起因果步驟，皆在某篇報告中以具體形式存活；被刪/併/抽象者已逐筆進損失帳本並附理由，無靜默丟棄。
19. **案例保全**：候選貼文的具體案例與細節未以「重複」為由被去重吞掉；殊途同歸的多個事故皆保留，案例段未壓縮成一句帶過。
20. **報告清單鎖定**：報告清單已凍結（每 slot 四欄齊全，`緣起來源` 欄留 session 內）；series-map 僅呈現去痕後 slot；最終報告篇數未低於鎖定數，任何 slot 的合併/刪除皆已進損失帳本附理由並重過合併條件，無靜默併篇。
21. **展開下限**：§2 反推卡末三欄（潛在子問題、未證成前提、暗藏多核心）已逐篇抽取；§3.6 展開機會盤點三類（拆分、潛在深化、跨篇湧現）皆給定去向，選 `本次不展開` 者附理由；判為 `本次展開` 者已實際發展，報告未停在原貼文描述深度。
22. **Metadata 落點**：`report.zh-TW.md` 正文以結論收束，結尾無 `series`／`tags`／「建議 metadata」區塊；再結晶後的 `series` 與逐報告 `tags` 記於 series-map.md。
23. **個案主軸與回推因果**：每個核心主張盡可能以具體個案為起點與骨幹（確屬純概念者至少附密度下限反例）；論證採「個案→回推因果→主張→邊界→通用化」，非主張先行配裝飾例；通用化結論皆由回推因果與個案賺得，達期刊論文層級的論證嚴謹度，且未墮入空泛學術腔或形式章節堆疊。
24. **收束指涉完整性**：結論中的數量詞、代詞與總結性指涉（如「三個問題」「四者」「上述」「這些防線」）皆能在緊鄰段落或同一段落中找到明確對應；若作為全文最後收束，應優先列成明確問句、命題或清單，避免只在作者腦中成立的指涉閉合。

## 9. 流程固化與執行檢核 (Process Hardening)

本工作流的步驟皆為**強制步驟**，不是建議。為確保每步確實執行、展開建議不被略過，採以下紀律：

1. **每步對應一個可檢查產物**：步驟未產出對應產物即視為未完成，不得進入下一步。產物分兩層：
   - **內部檢核產物**（如反推卡、候選清單、擴張去向標記、損失帳本、報告清單鎖含 `緣起來源`）：只用來驗證步驟確實執行，依 §5 只能留在 session 內部脈絡，**嚴禁進入任何可交付產物，且即使在 `--force-write` 下也嚴禁寫入磁碟**（落盤會保存正要抹除的來源痕跡，見 §7）。其去痕跡後的投影（如報告清單鎖的 slot 角色）才可進 series-map。
   - **可交付產物**（`report.zh-TW.md`、`guide.zh-TW.md`、`series-map.md`）：必須通過 §5 去痕跡化，不得出現原貼文痕跡。
2. **不得靜默略過**：任何「不做」的決定（如某展開類型選 `不需要`）必須留下理由，禁止留空欄位。
3. **盤點與鎖定先於重寫**：§3 步驟 6 的展開盤點表＋展開機會盤點、步驟 7 的報告清單（每 slot 四欄齊全）任一未完成，禁止進入 §4 任一篇重寫。
4. **篇數塌縮非預設**：§4 減少報告篇數或合併 slot，必須進損失帳本附理由並重過 §3 步驟 4 合併條件；靜默併篇視為未完成。
5. **展開非選配**：§2 末三欄與 §3.6 展開機會盤點不得整欄留空或一律填 `本次不展開`；判為 `本次展開` 者未實際發展、報告停在原文深度，視為未完成。

執行檢核表（每個 session 結束前逐列確認）：

| 步驟 | 必須產出 | 性質 | 對應閘門 |
| :--- | :--- | :--- | :--- |
| §0 邊界契約 | 未改 `content/`、未產 handoff JSON、未執行發布的確認 | 內部檢核 | 閘門 13 |
| §2 正文反推 | 每篇候選貼文一份反推卡 | 內部檢核 | 閘門 1、2 |
| §3 系列地圖 | 系列邊界、角色、因果順序 | 內部檢核（抽象後成為 series-map） | 閘門 7、8、10 |

## 核心規則 (Rules)

1. **正文優先**：已發布 front matter 是觀察資料，不是權威來源。
2. **單系列隔離**：一次 session 只處理一個母系列，以降低跨系列語境污染。
3. **吸收而非整理**：目標不是去重，而是吸收原貼文後重新結晶；吸收意味著緣起因果被重述，不是被精煉掉。
4. **合併是最後手段**：系列分篇是預設；合併只用於消除真正同構的重複文章。
5. **緣起保全**：去重只消除重複陳述，不消除緣起因果與具體案例；任何被刪/併/抽象的緣起步驟必須進損失帳本附理由，靜默吞掉視為未完成（壓縮下限與擴張上限對稱，見 §4b）。
6. **去管道、留緣起**：去痕跡化抹除的是來源/管道識別（slug、路徑、「重寫自」），不是問題當初如何發生的實質因果。
7. **結構勝過形容**：能用 Mermaid 或 example code 呈現的因果、流程、契約與邊界，應優先外化成可檢查結構。
8. **輸出不得留痕**：可交付產物不得引用或指向原貼文；來源只作輸入材料，不作輸出依賴。
9. **報告仍是報告**：本流程產物比照結晶報告，不直接成為貼文或 handoff。
10. **發布另行委派**：若要發布，必須經人工審查後交給 `init-handoff`。
11. **共用前提就地自含**：跨多系列的前提不抽成中央報告、不跨 session 引用，用到的系列就地重述，措辭保持一致。
12. **步驟即契約**：每步對應一個可檢查產物，展開盤點不得留空，靜默略過視為未完成。

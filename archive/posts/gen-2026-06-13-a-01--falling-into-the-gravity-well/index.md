## 引言：重寫不是翻譯，而是重新建立世界

當一個 Legacy 系統變得難以維護，跨語言重寫看起來往往像逃生門。舊系統可能是 Python、Ruby、PHP、Java 或某個歷史版本的框架；新系統則可能選擇 Rust、Go、TypeScript、Kotlin 或更現代的雲原生架構。團隊希望藉由新語言、新型別系統、新部署模型與新工具鏈，擺脫過去累積的複雜度。

AI 的出現讓這個願望變得更誘人。過去跨語言重寫需要大量人力考古；現在似乎只要把舊代碼餵給模型，就能產出一個語法正確、結構清楚、甚至帶有測試的新版本。這看起來像是現代化的捷徑，實際上卻可能是最危險的陷阱。

因為系統重寫的核心不是語言轉換，而是語義、邊界與架構範式的重建。若 AI 被要求「忠實翻譯」舊代碼，它會努力保留舊系統的行為形狀；但舊系統之所以需要重寫，往往正是因為那些形狀已經承載了太多歷史包袱。於是 AI 不是帶團隊逃離 Legacy，而是把 Legacy 的重力井搬到新語言裡。

跨語言重寫最可怕的失敗，不是新系統沒有跑起來，而是它跑起來了，測試也通過了，卻把舊系統的錯誤抽象、隱性狀態、測試束縛與事故遺產全部重新封裝成一個更難拆的新宇宙。

## 一、Legacy 重力井是什麼

所謂重力井，是指舊系統形成的慣性場。它不只存在於代碼裡，也存在於測試、部署、資料、操作習慣、團隊記憶與業務方對「相容」的想像中。當團隊試圖重寫系統時，這些力量會把新系統拉回舊世界。

這種重力有幾種來源：

1. 舊代碼的結構讓人誤以為它就是業務本身。
2. 舊測試把實作細節偽裝成行為契約。
3. 舊 bug 因為被使用者或下游服務依賴，而變成事實上的 API。
4. 舊系統的效能問題與補丁被壓縮成原作者的直覺，沒有文件化。
5. 新語言的範式尚未建立，於是團隊用舊語言的思維寫新語言。

AI 會放大這個重力井，因為它非常擅長模仿上下文。當上下文主要由舊代碼提供，AI 就會把舊系統當成權威。它會推斷：「既然舊系統這樣寫，新系統應該也要保持同樣的結構。」但重寫真正需要的不是同形轉換，而是判斷哪些語義應該保留，哪些形狀必須丟掉。

## 二、陷阱一：隱性狀態的災難轉譯

許多 Legacy 系統依賴隱性狀態。這些狀態可能藏在全域單例、動態 monkey patch、執行緒區域變數、框架生命週期、快取副作用、資料庫 session 或長年累積的物件欄位中。舊語言或舊框架可能容許這種寫法，甚至讓它在小團隊和低併發場景中顯得方便。

跨語言重寫時，AI 若被要求保留語義，就會試圖在新語言中重建這些隱性狀態。問題是，新語言可能有完全不同的哲學。例如 Rust 強調所有權與顯式生命週期，Go 鼓勵簡單並發與明確資料流，函數式風格鼓勵不可變資料與純函式。若把舊系統的隱性狀態硬塞進新語言，AI 常會生成全域鎖、共享 mutable state、過度寬鬆的 singleton 或複雜的上下文傳遞。

舊系統可能長這樣：

```python
class OrderProcessor:
    _instance = None

    def __init__(self):
        self.state = "idle"
        self.current_order = None

    def process(self, order):
        self.current_order = order
        self.state = "processing"
        # 呼叫多個外部服務，期間修改內部狀態
```

AI 在 Rust 中為了維持形狀，可能生成：

```rust
lazy_static! {
    static ref PROCESSOR: Arc<Mutex<OrderProcessor>> =
        Arc::new(Mutex::new(OrderProcessor::new()));
}
```

這看似是合理翻譯，實際上卻把舊系統的隱性序列化變成新系統的效能瓶頸。更糟的是，因為新語言本來提供了更好的模型，例如將每筆訂單處理成獨立狀態機、用 message passing 隔離副作用、用明確 transaction boundary 管理資料，這些可能性都被「忠實翻譯」壓扁了。

問題不在全域鎖本身，而在 AI 以語義相容為名，保留了舊架構中最該被淘汰的部分。

## 三、陷阱二：白盒測試把舊實作偽裝成契約

許多團隊在重寫時會先翻譯測試。他們認為，只要新系統通過舊測試，就代表行為相容。這個想法只在一種情況下成立：舊測試真的描述外部行為，而不是綁死內部實作。

現實中，Legacy 測試常常是白盒測試。它們檢查某個私有方法是否被呼叫，mock 掉特定類別，依賴動態語言的 monkey patch，驗證中間狀態，甚至測試某個歷史 bug 的具體形狀。這些測試不是系統契約，而是舊實作的影子。

當 AI 被要求「翻譯測試並讓新系統通過」，它會把這些影子當成真理。結果新系統的 API、模組邊界與內部結構，會被迫長得像舊系統。團隊原本希望利用新語言建立更清楚的邊界，最後卻為了通過舊測試而保留相同的耦合。

這種情況尤其容易發生在以下測試中：

1. 測試 private method 或內部 callback 順序。
2. mock 過深，導致新系統必須保留舊依賴圖。
3. 驗證中間資料結構，而非最終可觀測結果。
4. 依賴舊框架生命週期或全域狀態。
5. 把 bug-compatible 行為當成正確行為。

真正應該保留的是黑盒行為：輸入、輸出、狀態轉移、錯誤語義、權限邊界、可觀測事件與資料不變量。舊測試可以作為考古材料，但不能自動成為新系統的法律。

## 四、陷阱三：Bug 相容性與隱性邊界混在一起

重寫時，業務方常說「行為必須 100% 一致」。這句話看似合理，因為重寫不應破壞使用者。但它同時也是陷阱，因為舊系統的「行為」裡混雜了三種不同東西：

1. 真正的業務契約。
2. 因歷史限制形成的實作偶然。
3. 被下游依賴的 bug 或副作用。

如果不先分類，AI 會把三者一起搬過來。更麻煩的是，有些看似 bug 的東西其實是隱性邊界。例如某段奇怪的 sleep 可能是在避免舊資料庫鎖競爭；某個不優雅的重試順序可能是在避開第三方 API 的節流策略；某個看似多餘的欄位可能是舊版客戶端判斷狀態的唯一依據。這些就是所謂的卻斯特頓籬笆：在不知道它為何存在之前，不能輕易拆掉。

AI 在這裡會有雙重風險。它可能過度「清理」，把看似醜陋但重要的防線移除；也可能過度忠實，把明明應該修掉的 bug 當成相容性需求永久化。

因此，重寫前必須建立一個分類流程：

1. 哪些行為是明確契約，必須保留。
2. 哪些行為是歷史偶然，可以改變但需要遷移策略。
3. 哪些行為是 bug，但已有下游依賴，需要相容層或公告期。
4. 哪些行為是防禦性補丁，必須理解原因後才能重新設計。

沒有這個分類，AI 的「忠實」和「優化」都可能造成事故。

## 五、陷阱四：原作者 PoC 的定錨效應

跨語言重寫時，原作者常會先寫一份新語言 PoC，作為 AI 或團隊的參考。這看起來很合理，因為原作者最懂系統。然而這份 PoC 也可能成為最強的污染源。

原因是原作者的直覺通常壓縮了大量歷史知識。他知道哪些地方不能動，知道哪裡會壞，知道某些設計為什麼存在。但當他快速寫 PoC 時，這些知識不一定會被完整表達成因果鏈。PoC 可能只呈現「應該大概這樣」，卻沒有說明「為什麼不能那樣」。AI 讀到 PoC 後，會把它當成高權重上下文，並沿著 PoC 的形狀繼續生成。

如果 PoC 本身是「新語言外皮包著舊架構靈魂」，AI 就會被定錨。它會順從原作者給出的局部形狀，而不是探索新語言真正適合的設計。最後，新系統不但沒有擺脫舊世界，還因為原作者的權威感而更難被質疑。

這不是原作者的錯，而是知識壓縮的自然結果。專家很容易跳過自己以為顯而易見的因果。AI 則會把看得見的 PoC 當成比看不見的直覺更真實的資料。

## 六、正確路徑：從代碼考古轉向黑盒考古

跨語言重寫不應以舊代碼為直接藍圖，而應以舊系統的可觀測行為與業務不變量為材料。這可以稱為黑盒考古。

黑盒考古不問「這段舊代碼如何翻譯」，而問：

1. 系統對外承諾了什麼。
2. 哪些輸入會導致哪些狀態轉移。
3. 哪些錯誤語義是呼叫端依賴的。
4. 哪些資料欄位是權威，哪些是衍生。
5. 哪些非功能需求不可退讓，例如延遲、吞吐、隔離、審計。
6. 哪些歷史事故塑造了現在的邊界。

舊代碼仍然重要，但它是證據，不是藍圖。舊測試仍然有用，但它是線索，不是法律。原作者仍然關鍵，但他的直覺需要被解壓縮成可檢查的規格，而不是直接包進 PoC。

## 七、AI 在重寫中的正確位置

AI 不應扮演翻譯機，而應扮演幾種更受控的角色。

第一，AI 可以做考古助手。它能幫忙整理舊代碼中的入口、資料流、外部依賴、錯誤處理與測試覆蓋，但輸出應被視為假設清單，需要人驗證。

第二，AI 可以做反例產生器。讓它根據候選設計列出可能破壞相容性的場景，逼團隊釐清哪些相容是必要的，哪些只是歷史包袱。

第三，AI 可以做新語言 idiom 的展開器。在人類已經定義好系統契約後，AI 可以協助把規格實作成符合新語言慣用法的模組，而不是照舊代碼逐行翻譯。

第四，AI 可以做測試矩陣擴充器。人先定義黑盒契約，AI 再協助產生邊界案例、故障注入、狀態轉移測試與遷移驗證。

這樣使用 AI，才能讓它協助逃離重力井，而不是把重力井複製得更快。

## 結論：逃離 Legacy 的第一步，是拒絕忠實翻譯

跨語言重寫的目標不是用新語法重現舊世界，而是把舊系統中真正有價值的業務語義洗出來，然後用新語言、新架構與新運行環境重新建立它。

AI 讓重寫變快，也讓錯誤路徑變得更有誘惑力。逐行翻譯、白盒測試搬運、bug 相容崇拜與 PoC 定錨，都會把團隊拉回 Legacy 重力井。真正可靠的重寫必須先暫停對代碼形狀的忠誠，轉而忠於系統契約、失敗語義與歷史因果。

只有當舊代碼從藍圖降級為證據，舊測試從法律降級為線索，原作者直覺從口令升級為規格，AI 才能成為現代化的力量，而不是 Legacy 的複製機。

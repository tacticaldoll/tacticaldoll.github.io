## 背景

一個多人維護的軟體專案決定重構治理結構，將散落的知識遷移到新的歸屬位置。邏輯上最直接的做法是：在舊位置設立攔截——放置 README 說明「此目錄已廢棄」、加 CI 檢查阻止新檔案寫入、通知現有作者遷移內容。

這個方案在提出後被否決了。原因不是技術上做不到，而是部分開發者明確表示：不希望改變現有工作方式。

否決之後，需要設計一個替代方案——一個不阻擋寫入、但仍然能在長期收斂到目標狀態的知識管理機制。這個替代方案的核心隱喻是：排水口，而非水壩。

## 分析

### 知識熵：多作者系統的必然產物

在熱力學中，封閉系統的熵只增不減。在多人維護的軟體專案中，知識有類似的傾向：隨著時間推移，知識自然地變得更分散、更重複、更過期。

這不是任何人的錯。每位開發者在自己的時間、以自己的脈絡寫下知識。一個人寫了 `cache-arch.md` 描述快取設計，另一個人在 openspec spec 中以 WHEN/THEN 格式定義了同一個快取的行為需求。兩份文件各自正確，但合在一起就是冗餘。第三個人在程式碼的 module doc 中寫了快取的實作概述——又是一份部分重疊的記錄。

這種知識熵在以下條件下加速增長：多位作者各有偏好的寫作位置、專案同時存在新舊兩套知識體系（如正在導入結構化工作流）、沒有統一的「新知識該寫在哪」指引。

### 水壩模式：對抗式治理

面對知識熵，最直覺的反應是築壩——阻止熵的來源。

具體做法包括：在已廢棄的目錄放 README 重導、在 CI 中加 linter 拒絕新檔案、code review 時強制要求遷移到新位置、發通知要求現有作者清理自己的舊文件。

水壩模式的底層假設是：**如果我們能阻止新的混亂進入，現有的混亂就能被逐步清理。** 進水量降到零，排水慢慢做，終究會乾。

這個假設在理想條件下成立。但在多人維護的專案中，理想條件很少存在。

水壩失敗的常見模式如下。首先是繞道——開發者發現 context/tech/ 被攔了，就在其他地方寫（比如 PR description、Slack 訊息、或程式碼註釋中的長篇說明），知識熵沒有減少，只是從一個可管理的位置流向了更分散的位置。其次是抵觸——被攔截的開發者會覺得「這個規範是額外的負擔」，而非「這是更好的做法」。當一個規範被感受為負擔，它的遵守率會隨時間下降。最後是維護成本——CI 檢查需要維護白名單（哪些舊檔案可以更新但不能新增？），README 需要保持最新，通知需要有人跟進。這些都是持續性的成本。

水壩模式在小團隊、單一決策者、或強文化規範的環境中可能有效。但在多作者、多工作習慣、且部分成員明確反對改變的環境中，它的成本常常超過收益。

### 排水口模式：非對抗式治理

替代方案不阻擋進水，而是在出口端持續排水。

核心設計是一個「消解循環」——一組固定的步驟，在每次結構化工作流的里程碑（如 openspec change 歸檔）之後執行：

1. 比對新產出的規格與舊知識庫，找出已被覆蓋的內容
2. 刪除或標記已覆蓋的內容
3. 檢查是否有人在舊位置新增了內容，將其分流到正確位置
4. 判斷是否產出了跨模組的穩態知識，決定其歸屬

這個循環不依賴任何人改變行為。開發者繼續在習慣的位置寫，消解循環在下一個里程碑時吸收並重新分配。

排水口模式的底層假設與水壩相反：**混亂的進入是不可避免的，重要的是排出速率能否跟上。** 只要每個里程碑的消解量 ≥ 期間的新增量，系統就在收斂。

### 收斂條件

排水口模式並非無條件有效。它的收斂依賴三個前提：

第一，排水必須有觸發機制。如果消解循環只是一個「建議」——「歸檔後記得清理一下」——它會被遺忘。有效的觸發是將消解寫入永遠載入的指引（如 CLAUDE.md），讓 AI agent 在每次歸檔後自動執行。人類開發者可能不做，但 agent 會做。

第二，進水速率必須是有界的。如果專案在快速擴張、大量新人同時寫入、或者有外部來源持續灌入知識，消解循環的速率可能追不上。排水口模式適合「穩態維護」階段——團隊規模穩定、寫入頻率可預期。

第三，必須存在「正確位置」。消解循環的分流步驟需要知道每種知識該去哪裡。如果目標位置不明確（新體系本身還在設計中），分流就無法執行。這要求治理框架在啟動消解之前已經建好——治理奠基先於知識遷移。

### 與分散式系統的類比

排水口模式與分散式系統中的「最終一致性」（eventual consistency）有結構性的相似。

在**強一致性**（Strong Consistency） <!-- term:StrongConsistency -->系統中，每次寫入都立即同步到所有節點——相當於水壩模式，每次寫入都被攔截並導向正確位置。優點是系統在任何時刻都是一致的。缺點是寫入延遲高、系統可用性低（任何節點故障都阻塞寫入）。

> [!IMPORTANT]
> **強一致性** <!-- term:StrongConsistency --> (Strong Consistency): 分散式系統或數據管理中的一種一致性模型，要求所有讀取操作都能立即獲取到最新寫入的數據，以確保所有節點看到的數據狀態完全一致。 <!-- anchor:StrongConsistency -->


在最終一致性系統中，寫入可以發生在任何節點，系統不保證即時一致，但保證在一段時間後所有節點會收斂到相同狀態——相當於排水口模式，寫入不被阻擋，但定期的消解循環將系統推向一致。

最終一致性的適用條件是：暫時的不一致是可容忍的、寫入的可用性比即時一致性更重要、存在可靠的收斂機制。這三個條件在知識管理場景中通常成立：短暫的知識重複不會造成系統故障（可容忍），開發者的寫作流暢性比知識位置的即時正確性更重要（可用性優先），消解循環是可靠的收斂機制。

### 妥協的經濟學

非對抗式治理本質上是一種經濟決策——在「治理精確性」和「團隊摩擦」之間取捨。

水壩模式追求高精確性：每份知識都在正確位置，沒有冗餘，沒有過期。但它的成本是團隊摩擦——攔截 = 打斷工作流、強制學習新工具、對不遵守者施壓。

排水口模式接受低精確性（暫時的）：知識可能暫時在錯誤位置，存在短暫的冗餘。但它的收益是零摩擦——沒有人被要求改變行為，沒有人被攔截，沒有人被通知。

在一個有 N 位開發者的專案中，水壩模式的總成本是 N × (學習成本 + 行為改變成本 + 被攔截的挫敗感)。排水口模式的總成本是 M × (每次消解循環的執行成本)，其中 M 是里程碑數量。當 N 大於某個閾值、或者行為改變成本特別高（開發者明確反對）時，排水口模式的總成本更低。

這不是一個永恆的最優解。當團隊逐漸適應新工作流，寫入舊位置的頻率自然下降，排水口的工作量也隨之減少。屆時可以重新評估是否需要更積極的治理——但那是在團隊準備好之後，不是在今天。

## 省思

### 排水口模式的隱含要求

這個模式聽起來優雅，但有一個常被忽略的前提：**必須有人（或 agent）持續執行消解循環。** 如果循環停止——因為忙、因為忘記、因為 agent 的指引被修改——排水口就堵住了，系統回到純進水狀態。

這就是為什麼消解循環被寫入 CLAUDE.md 而非某個「最佳實踐」文件。CLAUDE.md 永遠載入，agent 永遠看到它，歸檔後的消解步驟不會被遺忘。這是排水口模式的基礎設施——它的可靠性取決於觸發機制的可靠性。

### 不是所有知識都適合排水

排水口模式適合「知識位置錯誤但內容有價值」的情況。但有些寫入是真正的噪音——過期的設計筆記、已被否決的方案記錄、重複貼上的 Stack Overflow 片段。對這些，消解循環的正確動作是刪除，不是分流。

區分「值得分流的知識」和「應該刪除的噪音」需要判斷力。AI agent 在執行消解循環時，可以根據 **描述性知識**（Knowledge） <!-- term:Knowledge --> Contribution Rules 的路由表做初步分類，但最終判斷可能需要人類確認。這是完全自動化消解的邊界。

> [!IMPORTANT]
> **描述性知識** <!-- term:Knowledge --> (Knowledge): 逆向工程產出的描述性知識，在專案中被視為債務指標 <!-- anchor:Knowledge -->


### 與日本 5S 的差異

排水口模式表面上類似日本 5S 方法論中的「整頓」（seiton，定位管理）和「清掃」（seiso，定期清理）。但有一個關鍵差異：5S 要求所有成員遵守「用完放回原位」的紀律。排水口模式不要求這個——它接受「有人不放回原位」的現實，用後端的清理彌補前端的缺失。

這個差異反映了適用場景的不同。5S 適合實體工廠——物品的位置直接影響安全和效率，「不放回原位」的成本高到必須強制。知識庫的「位置錯誤」成本低得多——暫時的冗餘不會讓系統崩潰，只是增加查找成本。當錯位成本低時，強制紀律的投入產出比不划算。

## 結論

非對抗式知識熵管理的核心原則可以歸結為三點：

1. **不阻擋進水，持續排水。** 在多作者環境中，試圖從源頭阻止知識熵的增長比吸收後定期清理更昂貴。設計出口端的消解機制，而非入口端的攔截機制。

2. **收斂速率 ≥ 增長速率 = 系統終將一致。** 排水口模式的數學很簡單。確保消解循環的觸發機制可靠（寫入永遠載入的指引），確保消解速率足夠（每個里程碑清理一輪），系統就在收斂。

3. **妥協是一種經濟決策，不是原則讓步。** 選擇不攔截不是放棄治理，而是在「精確性」和「摩擦」之間選擇了當前階段的最優解。當團隊準備好了，可以隨時收緊。但收緊應該是團隊自然演化的結果，不是外部強加的規範。

## 背景

軟體團隊一向靠外化知識來協作。文件記錄決策，coding standard 統一風格，review checklist 確保品質——這些文字產物是團隊共享認知的載體。在 AI 加入協作後，這些產物多了一個讀者：Agent。同一份 commit message 既要讓人類 reviewer 理解變更意圖，也要讓 Agent 在未來的 context 中正確引用歷史脈絡。同一份規格文件既是人類的設計契約，也是 Agent 的行為指令。

當品質出問題時，管理者的本能反應是「加強外化」——更詳細的模板、更嚴格的格式規範、更多的自動化檢查。這個反應在傳統軟體工程中通常有效：人類讀者可以根據模板還原意圖，格式規範降低認知負擔，**檢查工具**（Linter） <!-- term:Linter -->攔截常見錯誤。

> [!IMPORTANT]
> **檢查工具** <!-- term:Linter --> (Linter): 在開發期或持續整合管線中，用以靜態掃描程式碼並揪出風格或語法錯誤的工具。 <!-- anchor:Linter -->


但當介質本身有結構性失真時，增加介質密度不是在修復問題，而是在放大問題。

## 分析

### Commit Log 的品質偏差

在一個具體的專案中，commit log 呈現明顯的品質偏差。部分 commit 有清晰的結構：變更意圖、影響範圍、與先前決策的關聯一目了然。另一部分則是機械式的描述——「修改了 X 檔案」「新增 Y 功能」——格式上符合要求，語意上幾乎為零。

這個偏差不與程式碼複雜度相關。簡單的變更可能有精確的 commit message，複雜的重構可能只有一行模糊描述。偏差的真正相關因素是操作者與 Agent 互動的品質——能夠引導 Agent 產出好 commit message 的人，本身就對「什麼資訊值得記錄」有清晰的判斷。

### 偏差的傳播鏈

品質偏差不是孤立的。它沿著協作鏈傳播，每一站都放大損失：

低品質的 commit message 意味著 reviewer 必須自己讀 diff 來重建意圖。Review 的認知負擔上升，品質下降——reviewer 更可能漏看問題，或者因為疲勞而放行不夠好的變更。這些變更進入 main branch 後，成為後續 Agent 的 context。Agent 從模糊的歷史中學到模糊的模式，產出進一步偏離預期。專案的知識基礎逐漸劣化，而每一個環節的參與者都覺得自己只是在處理上一個環節遞過來的問題。

**規格驅動開發**（Spec-Driven Development） <!-- term:SpecDrivenDevelopment -->中的 artifacts 呈現類似的模式。規格文件本應是意圖的精確表達，但當它的作者無法準確判斷 Agent 需要什麼程度的資訊時，文件要麼過度冗長（觸發 Agent 的選擇性關注），要麼遺漏關鍵約束（Agent 用自己的假設填補）。兩種情況都導致實作偏離意圖，而偏離被發現得越晚，修正成本越高。

> [!IMPORTANT]
> **規格驅動開發** <!-- term:SpecDrivenDevelopment --> (Spec-Driven Development): 以規格文件為基準約束程式碼行為，確保實作與規格始終對齊的開發方法。 <!-- anchor:SpecDrivenDevelopment -->


### 管理直覺的陷阱

面對品質偏差，管理策略的典型反應是加強外化：

- 導入 commit message 模板，規定格式與必填欄位
- 增加 CI linting 規則，自動檢查 message 結構
- 撰寫指南文件，說明「好的 commit message 應該長什麼樣」
- 在 review checklist 中增加 message 品質的檢查項

每一項都是在增加介質密度——用更多文字來約束文字的品質。這在短期內可能有效：模板確實讓最差的 commit message 變好了一些。但它產生了一個更隱蔽的問題：合規取代了溝通。

操作者開始填寫模板的欄位，而不是思考「這個變更的意圖是什麼」。模板成為一個可以機械式完成的表格，格式完美但語意空洞。CI 檢查通過了，因為所有欄位都有值；但 reviewer 的處境沒有改善，因為欄位裡的內容沒有資訊量。

### 規則棘輪

每一次品質事故都催生一條新規則。沒有對應的機制來移除過時的規則。結果是規則集只增不減——這就是棘輪效應。

棘輪的問題不只是數量膨脹。每條規則都和其他規則有潛在的交互作用。第三條規則要求 commit message 包含影響範圍，第七條規則要求訊息控制在 200 字以內，第十二條規則要求引用相關的 JIRA ticket——當三者同時適用時，操作者必須在彼此衝突的約束中做取捨。這個取捨本身就是一種判斷力，而它恰恰是規則試圖替代的東西。

## 省思

回看整個鏈條，一個模式浮現：品質偏差的表面原因是「有人寫了不好的 commit message」，管理對策是「用規則確保人寫出好的 commit message」。但真正的差異不在「知不知道好的 message 長什麼樣」——模板和指南已經回答了這個問題。差異在於操作者是否具備一種更底層的能力：理解 Agent 會怎麼處理他的輸入，並據此調整輸入的內容和方式。

高品質的操作者在寫 commit message 之前，已經在腦中模擬了 reviewer 和未來 Agent 讀到這段文字時會怎麼理解它。他的判斷不是來自模板，而是來自對介質特性的內隱理解。這種理解不是規則可以傳遞的——它是一種經由實踐內化的能力。

用更多外化規則來彌補這種能力的缺失，是在用有損介質修補有損介質造成的損傷。文字 artifacts 在從人到 Agent 的傳遞過程中有不可消除的編碼損耗和解碼損耗——規則是判斷力的有損壓縮，而 transformer 的處理又對這個有損版本進行二次變形。當管理策略的核心工具就是這個有損介質時，管理行為本身也受介質限制。增加介質密度（更多規則、更多文件、更多模板）不會提升協作品質，只會提升合規的外觀，同時把真正的品質問題推入更難觀測的角落。

這裡有一個容易被忽略的區別：高品質操作者的優勢不是「他知道更多規則」，而是他能預判介質的失真方向。他在寫 commit message 時已經在腦中建構了一個模型——reviewer 讀到這段文字會怎麼理解、Agent 在未來引用這段歷史時會怎麼權重——然後根據這個預判來調整措辭。這是一種對介質特性的內隱理解，不是任何模板能替代的。缺少這種理解的操作者，即使拿到完全相同的模板，產出的品質依然不同——因為模板只規定了結構，不提供填入結構的判斷力。

## 結論

當介質有結構性失真時，瓶頸不在介質的密度，而在使用介質的人的能力。管理策略需要從 artifact-centric（產出更多、更好的文件）轉向 capability-centric（發展人使用介質的判斷力）。這個轉向是不舒適的——能力發展緩慢、因人而異、難以量化——不像增加一份模板那樣立即可見、可度量。但介質的天花板已經劃定了外化路線的上限，繼續在這條路上投入資源，報酬率只會遞減。

這留下了一個核心問題：這種使用介質的判斷力到底是什麼？它從哪裡來？如果它是瓶頸，為什麼它不能像**技術技能**（Technical Skill） <!-- term:TechnicalSkill -->一樣被寫成指南、交給所有人執行？答案可能就藏在它的性質裡——它依賴的是即時情境判斷，而情境是無限的，有限的規則集無法覆蓋。

> [!IMPORTANT]
> **技術技能** <!-- term:TechnicalSkill --> (Technical Skill): 與工具、語法或具體操作程序相關的硬實力，其正確答案在不同情境下通常是穩定且標準化的。 <!-- anchor:TechnicalSkill -->

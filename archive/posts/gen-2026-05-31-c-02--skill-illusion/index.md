## 背景

「AI 賦能」是一個流行的組織敘事。它假設 AI 工具擴展了人的能力邊界——原本做不到的事情，有了 AI 就能做到。這個假設在特定條件下成立：AI 確實能讓一個人處理更大量的程式碼、更快地生成 spec、更全面地覆蓋 review 維度。

但有一種特殊的失敗模式被這個敘事遮蔽了：**人從來沒有具備某項能力，AI 工具製造了擁有這項能力的錯覺，而這個錯覺在 AI 失效時才被揭穿。**

這不是「技能萎縮」——萎縮預設能力曾經存在，只是因為不使用而退化。這是「**技能幻覺**（Skill Illusion） <!-- term:SkillIllusion -->」——能力從未存在，但工具的輸出讓人（和組織）誤以為它存在。

> [!IMPORTANT]
> **技能幻覺** <!-- term:SkillIllusion --> (Skill Illusion): 指 AI 賦能讓開發者產生自身具備相應能力的錯覺，實質上相關能力從未在組織或個人中真正存在，並在 Skill 堆積文化中自我強化。 <!-- anchor:SkillIllusion -->

## 分析

### 幻覺的產生機制

技能幻覺 <!-- term:SkillIllusion -->的產生需要三個條件同時成立：

**條件一：工具的輸出看起來像能力的產出。** 當一個開發者用 Claude Code 的 skill 生成了一份結構完整、格式正確的規格文件時，這份文件和一個資深架構師手寫的規格文件在表面上沒有區別。檔案存在、內容合理、格式合規。組織的流程系統（Jira ticket、MR review、CI pipeline）看到的是「規格文件已產出」，無法區分「人理解需求後撰寫的規格」和「人把需求描述餵給 LLM 後收到的規格」。

**條件二：驗證門檻低於產出門檻。** 多數組織的 review 流程檢查的是 artifact 的存在和格式，不是 artifact 背後的理解深度。**約束性規格**（Spec） <!-- term:Spec --> 有沒有？有。格式對不對？對。必填欄位全不全？全。Review 通過。但「寫這份 spec 的人是否真正理解了他描述的系統行為」——這個問題不在任何 checklist 上。

> [!IMPORTANT]
> **約束性規格** <!-- term:Spec --> (Spec): 以結構化或機器可讀格式定義的系統或 API 合約規範。 <!-- anchor:Spec -->


**條件三：回饋延遲夠長。** 如果 LLM 生成的 spec 在下一步實作時立即暴露問題，**幻覺**（Hallucination） <!-- term:Hallucination -->會被快速修正。但 spec 的問題通常在更下游才浮現——整合測試、生產環境、甚至是下個季度的需求變更試圖擴展這個模組時。回饋延遲越長，幻覺 <!-- term:Hallucination -->存續越久，組織對「這個人能寫出好 spec」的錯誤信念越根深蒂固。

> [!IMPORTANT]
> **幻覺** <!-- term:Hallucination --> (Hallucination): 大型語言模型在面對不實或矛盾資訊時，生成不符合客觀現實或超出脈絡之回應的錯誤現象。 <!-- anchor:Hallucination -->


### Skill 堆積文化

技能幻覺 <!-- term:SkillIllusion -->在組織中的表現之一是 skill 堆積文化。

在 Claude Code 的生態中，skill 是一種可分享的能力封裝。一個團隊成員可以開發一個 skill，分享給整個團隊使用。在健康的使用模式中，skill 封裝的是成熟的、經過驗證的工作流程——它代表的是「這個操作我已經理解透徹，所以把它自動化」。

但在「AI 賦能」的組織壓力下，skill 的數量變成了一種績效指標。「我們團隊有 30 個 skill」被等同於「我們團隊有 30 項 AI 能力」。堆積 skill 成為一種展示「AI 成熟度」的手段。

問題在於：skill 的數量和團隊的能力之間沒有必然關係。一個 skill 可能是深思熟慮的流程封裝，也可能是把一段未經驗證的 prompt 包了個殼。從外部看不出區別——兩者都有名字、有描述、能執行、產出結果。但前者在 LLM 行為漂移時可以被維護者修正（因為維護者理解底層邏輯），後者在漂移時就是壞了（因為沒有人真正理解它為什麼能 work）。

### 知識邊界的錯誤延伸

技能幻覺 <!-- term:SkillIllusion -->最危險的表現是把 LLM 當作知識庫來使用，超出了模型訓練資料的覆蓋範圍。

一個具體的場景：品保或客服團隊使用 AI agent 分析私有產品的事件紀錄——當機日誌、錯誤報告、客戶投訴。Agent 會產出結構化的分析報告：根因分類、影響範圍評估、修復建議。報告格式專業，邏輯鏈完整，讀起來像是一個資深工程師的分析。

但 LLM 的訓練資料中沒有這些私有產品的知識。它不知道這個產品的架構、不知道這個錯誤碼的含義、不知道這個模組在生產環境中的實際行為。它產出的「分析」是基於通用的軟體工程模式做的推測——用看起來像分析的格式包裝了一個統計推論。

這個推測有時候是對的——因為很多問題確實符合通用模式。但它的正確性是偶然的，不是因為模型理解了系統。使用者無法區分「基於理解的正確分析」和「基於通用模式的碰巧正確」，因為兩者的輸出格式一模一樣。

當推測錯誤時——例如把一個特定於該產品架構的問題歸因為通用的記憶體洩漏——使用者如果缺乏對產品架構的深入理解，就無法辨識錯誤。更糟的是，Agent 的分析會以高 confidence 呈現錯誤結論，因為它不知道自己不知道。

### 幻覺的自我強化

技能幻覺 <!-- term:SkillIllusion -->一旦建立，會通過組織流程自我強化：

```
AI 產出看起來專業的 artifact
  → 組織流程驗證通過（格式合規、欄位齊全）
    → 個人績效記錄「已產出高品質 spec / 分析報告」
      → 組織認定此人具備相關能力
        → 更多同類任務被分配給此人
          → 更多 AI 產出被記錄為個人能力
            → 幻覺固化為組織信念
```

打破這個迴路需要一個外部衝擊——**模型版本遷移**（Model Version Migration） <!-- term:ModelVersionMigration -->導致產出品質驟降、一次生產事故暴露分析報告的錯誤、或者一個新成員提出「這份 spec 的這段描述和實際系統行為不一致」。但這些衝擊的強度必須足以對抗已經固化的組織信念，而組織信念的慣性通常很大。

> [!IMPORTANT]
> **模型版本遷移** <!-- term:ModelVersionMigration --> (Model Version Migration): 指底層大型語言模型發生無聲更替，導致其行為、意圖理解和隱性規則產生全局性且難以察覺的無聲漂移。 <!-- anchor:ModelVersionMigration -->

## 省思

技能幻覺 <!-- term:SkillIllusion -->與模型版本遷移 <!-- term:ModelVersionMigration -->的交叉效應值得標記：

當 LLM 底層版本更替導致 skill 行為漂移時，偵測依賴人的直覺——「最近的 spec 讀起來不太一樣」。但直覺的前提是人對「正常」有準確的內隱記憶。如果人的「正常」認知本身就是在技能幻覺 <!-- term:SkillIllusion -->中形成的——他從來沒有真正理解過好的 spec 應該是什麼樣——那他的直覺基準就是錯的。他不會覺得「最近不太一樣」，因為他從來就沒有過準確的參照點。

這形成了一個交叉脆弱性：

```
模型遷移（地基在動）× 技能幻覺（人不知道自己不知道）
= 漂移無法被偵測
```

多數治理框架假設人類觀測者有能力判斷治理機制是否有效。技能幻覺 <!-- term:SkillIllusion -->質疑的是這個假設本身：如果觀測者的判斷基準從未被正確建立過呢？

回到治理**回饋迴路**（Feedback Loop） <!-- term:FeedbackLoop -->的核心結論：治理規則的增廢取捨，最終必須由理解治理目的的人來判斷——不能外包給工具。這句話成立的前提是——人確實理解治理的目的。技能幻覺 <!-- term:SkillIllusion -->的**警告**（Warning） <!-- term:Warning -->是：組織可能已經在不知不覺中把「理解」替換成了「有工具能產出看起來像理解的東西」。

> [!IMPORTANT]
> **回饋迴路** <!-- term:FeedbackLoop --> (Feedback Loop): 用於持續觀測治理機制運營效能的閉環系統，通常包含規則遵守率、規則有效性與治理摩擦成本三個觀測層次，藉以驅動治理規則的動態調整。 <!-- anchor:FeedbackLoop -->
> **警告** <!-- term:Warning --> (Warning): 術語審計中指出的潛在問題或警告 <!-- anchor:Warning -->

## 結論

技能幻覺 <!-- term:SkillIllusion -->不是個人層面的問題——它是 AI 工具的輸出品質與人的驗證能力之間的結構性落差在組織中的具體表現。AI 工具的輸出越專業、越格式化、越「像」人的產出，幻覺 <!-- term:Hallucination -->越難被辨識。

「AI 賦能」的敘事需要一個限定條件：AI 只能賦能那些使用者已經理解的能力。把 review 自動化，前提是你知道什麼是好的 review。把 spec 生成自動化，前提是你知道什麼是好的 spec。把事件分析自動化，前提是你理解被分析的系統。

沒有這些前提，AI 賦的不是「能」——是「能的外觀」。而外觀的崩塌只是時間問題。崩塌的速度取決於兩個因子的乘積：未被驗證的 AI 產出的堆積速度，以及組織辨識幻覺 <!-- term:Hallucination -->的能力衰減速度。兩者都在加速，而且彼此強化。
